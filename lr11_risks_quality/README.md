## 4. Технічний борг

| Поле | Значення |
| --- | --- |
| Записів у `techdebt.csv` | 3 |
| Разом годин на повернення | 30 годин |
| Стеля годин мого варіанта | 80 годин |
| Борг у відсотках від стелі | 37,5% |
| Рішення pay_now / pay_later / accept | 2 / 1 / 0 |

Звідки взявся борг: під час оцінювання та планування виявлено технічні складності адаптера API, кешування й синхронізації розкладу, а також push-сповіщень із фоновим виконанням. Частину робіт планується виконати відразу, а оптимізацію кешу та конфліктів синхронізації перенести на пізніший спринт, щоб не блокувати основну функціональність. 

Що я свідомо не гашу і чому: позиція TD-02 на 12 годин (pay_later) переноситься на пізніший спринт, оскільки спочатку необхідно перевірити основні сценарії. Позицій із рішенням accept немає, тому технічний борг без плану погашення свідомо не приймається.

Як я пояснив би цей борг замовнику: Частина робіт потрібна не для появи нових функцій, а для стабільності даних та повідомлень. Якщо відкласти ці роботи надовго, користувач може побачити застарілий розклад або не отримати повідомлення про зміну; тому 18 годин заплановано на першочергове усунення проблем, а ще 12 годин — на наступний етап.
