# Вибір підходу для трьох проєктів

Студент: Кудерчук (DSEngneer). Тема проєкту: Мобільний застосунок розкладу академії зі сповіщеннями про зміни.

## 1. Три кейси коротко

| Кейс | Обраний підхід | Критерій, який тягне проти | Ціна цього вибору |
| :-: | --- | --- | --- |
| C-1 | predictive | technology | Гнучкість, швидкість |
| C-2 | adaptive | release_cost| Швидкість |
| C-3 | hybrid | contract |Гроші |

## 2. Кейс C-1

Конфлікт критеріїв: Чіткі умови та вимоги показують predictive, тим не менш API яке є нестабільним, вимагає адаптивності, наразі ми залишились на predictive так як ми також маємо дотримуватись своїх ж обіцянок, та графіку.

Що робимо з критерієм, який тягне проти: Ізоляція API  копіювання та тестування з різними показниками в ізольованих умовах для визначення причин поломок, найдені причини вирішувати на API в період найменшого навантаження.

Відкинутий підхід: adaptive, плюсом швидкість реакції на поломки, що зменшить недовіру до нашого сервісу. Мінус неможливість застосування через фіксовані умови та бюджет.
Перший тиждень:Тестування нестабільного API (або його копії) в ізольованих умовах.

## 3. Кейс C-2

Конфлікт критеріїв: Це стартап,має високий ризик помилки в фінансах через що можливий напрям adaptive, але швидкість провірки та ціна помилки є вирішальною в успіху стартапа

Що робимо з критерієм, який тягне проти: Детальне рев'ю, з не менш детальним тестуванням, в ідеалі мати бекап версію, на випадок неочікуваної поведінки

Відкинутий підхід: Predictive, плюсом безпека фінансів, дасть нам спокій того що не буде проблем з транзакцією і подальших проблем з бюджетом та клієнтами що збільшить довіру клієнтів до нас. Мінус Втрата ще більшої кількості часу що може вбити реліз до того як продукт буде готово

Перший тиждень:Покращити процеси продуктових задач та фінансів, добавити правила рев'ю для фінансів (грошовий модуль)

## 4. Кейс C-3

Конфлікт критеріїв: Так само як і в першому кейсі, фіксовані умови вказують на predictive, adaptive не зможе вирішити всієї проблеми (проблему застарілості системи та "непонятки" зі сторони юристів), використаємо hybrid для зміни системи під потреби юристів, через що задовільнимо і фіндеректора збільшивши бюджет.

Що робимо з критерієм, який тягне проти: Фіксація бюджету та дедлайнів для фіндеректора, розробка нової системи в присутності юристів для швидких правок та розробки більш гнучкого рішення (їм з цим працювати потім).

Відкинутий підхід: Predictive, плюсом є легка звітність,мінус всі це дані фальшиві, через неправдиві стартові дані, що тягне за собою ще більші проблеми.

Перший тиждень: Копія даних з старої системи для оцінки та співпраця з юристами про подальшу роботу.

## 5. Стрес-тест контрактом

| Кейс | Рішення до конверта | Рішення після | Що змінилось у роботі PM |
| :-: | --- | --- | --- |
| C-1 | Predictive, головний конфлікт — technology. Нестабільне API тягнуло до adaptive, але фіксовані умови, бюджет і дата подання звітності вимагали predictive. | Predictive, головний конфлікт — technology. Підхід не змінюється: нестабільність API все ще потребує ізоляції, тестування та контрольованого виправлення, а дата подання звітності залишається незмінною. | PM отримує більше свободи в управлінні обсягом робіт, бо тепер фактичні години оплачуються за T&M. Треба вести облік годин, задач і фактичних витрат, регулярніше погоджувати прогрес із замовником та фіксувати результати тестів API. Ризик перевірки/виправлення API частково переїжджає з фінансового ризику перевищення фіксованого обсягу на ризик перевищення годин і витрат, але ризик пропустити дату звітності залишається у PM. |

Окремо: Коли контракт fixed price, а вимоги мінливі, PM може: Жорстко зафіксувати основи вимог і проводити зміни лише через запит змін. 
Ціна: так як повільні погодження й ризик конфліктів із замовником.

Альтернативно винести невизначені частини в окремі етапи/опції з чіткими критеріями приймання.  
Ціна: складніша декомпозиція та більше управлінських накладних витрат.

## 6. Власний проєкт

Тема: Мобільний застосунок розкладу академії зі сповіщеннями про зміни.

Обраний підхід: Hybrid.Предиктивною частиною будуть базові функції застосунку, орієнтовний обсяг робіт, бюджет і строк релізу. Адаптивною — деталі інтерфейсу, спосіб відображення розкладу та механіка сповіщень, які можна уточнювати після отримання зворотного зв'язку від користувачів.

Чому саме так: Для проєкту є обмежений строк — 10 тижнів, визначена ємність команди та бюджет 480 000 грн, тому повністю adaptive підхід може створити ризик виходу за ці обмеження. Водночас заздалегідь передбачити всі потреби студентів і викладачів складно, особливо щодо зручності використання розкладу та сповіщень.Патерном ризику може стати big bang реліз де всі функції перевіряються лише наприкінці. Hybrid дозволяє зменшити цей ризик: базову функціональність плануємо заздалегідь, але розробляємо її невеликими ітераціями та регулярно перевіряємо результат.Щоб уникнути пізнього тестування та подальших "костилів".

## 7. Робочий журнал

Перша ідея була зробити predictive підхід, оскільки в нас є відомі дати релізу, бюджет та невелика комана але враховуючи big bang реліз повний фікс вимог буде складним, особливо на старті. Даючи нашій команді контроль над строками та бюджетом даючи простір для тестів, обмеження все ще лишаються predictive але є гнучкість уточнення та ітерації вимог.
